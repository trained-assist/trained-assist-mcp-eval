# Ревью плана #124: что уже есть, что реально отсутствует и как мигрировать без поломок

## Главное

План написан так, будто каталог, реестр и тесты выбора надо строить с нуля. Это не так: примерно
70% §1–§3 и §6.1 уже реализовано и работает в проде. Если реализовывать план в его текущем виде,
получится **вторая копия правды** — параллельный реестр рядом с работающим. Это и есть основной
способ сломать систему, а не переименование как таковое.

Поэтому ревью построено как «что уже есть → что реально отсутствует → что делать», а не как
«вот план, давайте исполнять».

## Реальные пробелы (что надо делать)

1. **Level-2 — выбор по именам дешёвой LLM — отсутствует полностью.** Ноль тестов. Это главный
   недостающий кусок: без него переименование слепое.
2. **§4 разделение «можно раскрывать» / «можно вызвать» отсутствует.** Сейчас `isReady()` (нет
   токена) **прячет инструмент полностью**. Следствие: модель не может сказать «подключи HH» — она его
   просто не видит. Это дефект, видимый пользователем, и он ровно попадает в §4.
3. **Per-role / per-entitlement фильтра нет вообще.** Есть per-profile модули и `audienceDefaults`
   для playbook'ов, но не для инструментов.
4. **§5 семантическая близость между репозиториями отсутствует.** Есть только жёсткая проверка
   дублей имён. Детерминированная часть уже ловит живой дубль: `search_serp_free` в core и в
   search-skill.
5. **Имена не несут смысла.** Замер (см. `FINDINGS.md`): 90.7% точности, и потолок упирается в
   имена, а не в размер каталога. `gc_*` (17 шт), `weeek_*` (15), `hh_*` (63) — префикс вендора
   вместо действия. Четыре `*_api_call` и пять `*_discross` неотличимы по имени.
   `hh_evaluate_resume` vs `hh_evaluate_candidate` — различие только в описании.

## Ответ на главный вопрос: как имплементировать, чтобы ничего не сломалось

**Единственный необратимый шаг — переименование.** Всё остальное (каталог, политика видимости,
тесты) аддитивно и может выкатываться тёмным флагом. Поэтому:

1. **Сначала замер, потом переименование.** Без baseline переименование принимается на веру.
   Сделано: 90.7% на 97 задачах, профиль `free`, воспроизводимо по seed.
2. **Инвариант двух каталогов нельзя схлопывать.** `listTools()` и `listAllTools()` — разные
   контракты, схлопывание вернёт #1530.
3. **Никогда не звать `registry.callTool()` in-process.** Задокументировано в `src/mcp-action.js`:
   модули читают `USER_ID` в module-level const при require — in-process вызов в общем
   мультитенантном сервере даёт молчаливую утечку между пользователями. Любой новый код каталога
   обязан спавнить дочерний процесс.
4. **Имя и поведение не менять в одном PR.** Сначала новое имя как canonical + старое как alias,
   потом отдельный PR на удаление alias после инвентаризации потребителей.
5. **Всё новое — в отдельном репо, без общих рантайм-модулей с продом.** Так сделано:
   `trained-assist-mcp-eval`. Прод не трогается by construction.
6. **Прогоны — в GitHub Actions, не на прод-серверах.** Все 7 репо публичные, каталог строится
   клоном без секретов. LLM — через `free`-профиль llm-ladder (бесплатные ступени), не через
   платный хвост.

## Исправленный порядок миграции

План предлагает «инвентаризация → контракт → пилот → сборщик → проверки → переименование». По факту
инвентаризация и контракт частично сделаны, поэтому:

| Этап | Статус | Действие |
|---|---|---|
| 1. Инвентаризация и baseline | **сделано** | 280 инструментов, 90.7% baseline, `FINDINGS.md` |
| 2. Контракт реестра | частично | Принять существующий `contract.schema.json` + `action-provider-manifest.json` как основу, а не писать новый |
| 3. Пилот на близких инструментах | **начат** | Пары `hh_evaluate_resume`/`hh_evaluate_candidate`, `demo_*` vs `hh_*` — готовый материал |
| 4. Сборщик полного каталога | **сделано** | `src/catalog.mjs`, детерминированный, CI-гейт на дубли |
| 5. Проверки близости | следующий | Детерминированная часть есть; семантическая — нужна, есть что проверять |
| 6. Переименование по репозиториям | последнее | Только после того, как новые имена не ухудшают 90.7% |
| 7. Периодические проверки | **сделано** | CI: catalog на каждый PR, eval по расписанию |
| 8. Оптимизация | — | После подтверждения качества |

## Про «5 репозиториев»

Их семь, не пять: `trained-assist-agent` (core, 127 инструментов) + шесть sibling-скилов
(hh 62, sales 53, documents 18, freelance 14, engineering 4, search 2). Плюс `zerocreds-mcp` —
восьмой, отдельный, единственный на настоящем MCP SDK, без тестов и CI. План стоит поправить:
либо включить все восемь, либо явно сказать, что `zerocreds-mcp` вне scope.

## Каталог зависит от ветки (обнаружено в ходе инвентаризации)

Локальные чекауты сидели на feature-ветках, `main` сильно впереди: 280 инструментов против 331.
`trained-assist-engineering` вырос с 4 до 40. Значит:

- «полный каталог» без привязки к коммитам — не определённость, а не артефакт. Любой реестр обязан
  записывать коммиты, иначе переименование по одной ветке и продолжение по другой переименуют
  разные наборы.
- Baseline на feature-ветках дал 90.7%, на `main` — 90.2%. Качество от размера каталога не зависит,
  премиса §1 подтверждается. Но приёмку надо вести по `main`.
- Реестр `trained-assist-agent` требует `npm ci` (better-sqlite3), шесть sibling — работают с голого
  клона. Асимметрия — аргумент за §3 «каждый репозиторий публикует manifest»: закоммиченный
  манифест избавил бы от установки зависимостей вообще.

## Что уже сделано в рамках этой работы

Репо [`trained-assist/mcp-eval`](https://github.com/trained-assist/trained-assist-mcp-eval):

- `src/catalog.mjs` — детерменный сборщик names-only каталога из 7 репо, с детектором дублей.
- `src/eval-select.mjs` — Level-2 eval на `free`-профиле llm-ladder, с фиксацией отработавшей
  модели, shuffle каталога, отвлекающими инструментами и параллельными прогонами.
- `tasks/selection.v1.jsonl` — 97 задач: синонимы, опечатки, похожие пары, вложенные,
  «инструмента нет», неоднозначные, без доступа, прямые вызовы.
- `FINDINGS.md` — разбор baseline и список проблем в именах.
- CI: `catalog` на каждый PR (без секретов), `eval` по расписанию (с `LADDER_TOKEN`).

**Baseline: 90.2% (175/194), 0 unavailable, 0 ошибок парсинга** на `main` всех семи репозиториев.

## Следующие шаги по приоритету

1. Принять baseline как порог приёмки переименования.
2. §4: разделить reveal и call — инструмент без токена должен быть виден со статусом «нужно
   подключить», а не исчезать. Это чинимый пользовательский дефект.
3. §5: семантическая проверка близости — начать с пар из `FINDINGS.md`.
4. Только потом — переименование по репозиториям с aliases.
